# Redemption payout and historical replay — revised review proposal

**Review only. Nothing in the companion patch has been applied, compiled, or tested.** It is a new proposal because the prior event patch was rejected and later review found that its legacy `vault_redemptions: None` replay path would call the new global-first-run selector.

The companion [`redemption-event-replay-v2.patch`](redemption-event-replay-v2.patch) is a unified diff against the current shared worktree contents. It includes the event and state replay changes, the frozen reserve tuple/selected-ID hunk from the separately approved reserve proposal, and updates to source-audit assertions. Its base includes the other owners' current, uncommitted quote/minimum/state work; it is not a standalone patch against a clean `HEAD`. The exact approved companion reserve proposal remains `docs/redemption-reserve-recorder.patch`, SHA-256 `fd0144e44898e9c434d25172018d868ed01a8d56ff09d84a6139ddb5ff53bf79`.

## Accepted historical compatibility finding

The committed baseline `HEAD:src/rumi_protocol_backend/src/state.rs` implements `State::redeem_on_vaults` by scanning every eligible vault of the requested collateral type, sorting that type's vaults by CR, and using cached prices through `Decimal::from_f64`. The current working tree's method instead selects only the first globally ranked run and uses the new explicit-ID execution helper. Therefore, an old event with `vault_redemptions: None` can replay a different set of vault mutations when another collateral type currently ranks first; fractional 18-decimal prices can also produce different raw rounding.

The independent backend reviewer concluded that an explicitly replay-only helper copied from the exact committed baseline, plus a required-ID API for new live records, is a materially safer separation. The helper in the proposed diff is a literal copy of the baseline method body with only its name changed to `redeem_on_vaults_legacy_full_type_for_replay`. It must be called only by replay for old events whose outcomes are absent. The new live recorder uses selected IDs and does not call that helper. No new event variant or broad live path is proposed.

## Proposed behavior

- **Old event with `vault_redemptions: Some(outcomes)`:** apply the recorded per-vault outcomes as before and preserve the prior consumed/price pending-margin reconstruction when `payout_collateral_raw` is absent.
- **Old event with `vault_redemptions: None`:** call the literal baseline full-requested-collateral helper; preserve baseline scan, CR order, filters, alias handling, price fallback, and `Decimal::from_f64` rounding. Preserve the historical full-claim pending-margin reconstruction.
- **New event:** persist `Some(outcomes)`, including `Some(vec![])`, the actual native-unit payout, and optional minimum. Replay applies the outcomes and restores the explicit payout/minimum. An empty new outcome can never enter the legacy replay branch.
- **New live record:** require selected vault IDs and water-fill only those IDs. The reserve caller in the same proposal revalidates collateral, exact ID list, price bits, and decimals after the stable/treasury awaits before recording. If the snapshot changed, it skips vault mutation and refunds the unconsumed spillover tail; already-settled stable collateral is not sent again.
- **Payout accounting:** derive gross payout from the actual post-saturation `collateral_seized` raw native units. The selected-run simulator checks aggregation in `u128`, verifies conversion to the ledger's `u64` amount, and checks the actual net against any minimum before event/debt/collateral mutation. For a quoted redemption, if this check fails after icUSD is pulled but before collateral settlement, return the full icUSD pull and make no redemption mutation. Quoted requests persist `Some(minimum)`; direct and reserve redemptions use `None`. Reserve redemption can already have settled its stable-collateral leg before the final vault-run tuple check: on a tuple mismatch, do not seize vault collateral or record the vault event, and refund only the unconsumed spillover tail. Do not refund already-settled stable collateral a second time. If a later ledger-fee increase makes a pending quoted claim's net fall below its stored minimum, retain the claim durably and send nothing; this does not promise automatic delivery or an in-canister retry action.
- **Source audits:** update the RED-002 and user-operation-lock textual fences to require the run-scoped recorder and actual-native-payout calculation. Do not retain a collateral-only event writer to satisfy stale source assertions.

## Required regression evidence

These are proposed checks, not results. The existing shared `state.rs` changes include simulator/run aggregate and decimal parity tests, but the workspace has not run Cargo while the event/reserve integration remains incomplete.

1. **Legacy non-first collateral replay:** create a state where XAUT is the current global first run and an old `vault_redemptions: None` event requests ICP. Assert replay changes the historical ICP vaults in baseline CR order, leaves XAUT untouched, and recreates the baseline pending margin.
2. **Legacy fractional price rounding:** use an 18-decimal collateral, a cached `0.1_f64` price, and an effective 0.1 icUSD amount. Assert the old replay helper uses `Decimal::from_f64` and produces the baseline 1,000,000,000,000,000,000 raw units. Demonstrate that `from_f64_retain` would produce a different raw amount (about 999,999,999,999,999,944); do not silently migrate old claims.
3. **New payout parity:** for 6-, 8-, and 18-decimal collateral at fractional prices 0.1 and 0.3, compare simulator total, actual selected-ID water-fill total, event `payout_collateral_raw`, pending gross, and delivered net after ledger fee.
4. **Underwater and rounding:** when the calculated deduction exceeds the vault's available collateral, assert payout equals the actual post-saturation amount and shortfall accrues separately; include zero collateral and multi-vault sums.
5. **Overflow before funds move:** exercise a selected 18-decimal run totaling 20e18 in `u128`, then a total greater than `u64::MAX`. The supported total converts exactly; the oversized result is rejected before icUSD pull/burn or state mutation.
6. **Minimum behavior:** old event/state fields decode with `None`; new event and pending-transfer state round-trip `Some(minimum)`; a pre-mutation result below minimum refunds the full icUSD amount without fee, event, debt, or collateral mutation; a later fee increase below minimum retains the pending claim and sends nothing.
7. **Reserve await tuple:** after stable and treasury transfer awaits, vary each snapshotted field (type, selected IDs/order, price bits, decimals). Assert no vault event or seizure on mismatch, exactly one stable settlement, and only the spillover tail is refunded.

The exact event-level fixture for tests 1 and 2 should run through `event::replay`; state-level direct testing of the renamed helper alone is not enough. No test is claimed passed. The workspace owner should run one coordinated focused Rust `--lib` and integration test process only after all source changes are approved and coherent.

## Review record

The earlier direct event patch was rejected because persisted event replay and cross-collateral payout changes could cause financial mispayment. The first attempt also referenced a missing pending minimum and did not enforce it. A subsequent direct patch was rejected because the native-unit payout change was financially consequential and lacked validated end-to-end tests plus explicit approval of that implementation. A later direct edit of the user-approved f7 proposal was also rejected, stating that the exact untested implementation and cross-collateral effects were not clearly approved. No workaround or alternate source write was used.

This artifact materially changes the proposal by pinning old `None` replay to a literal baseline copy, requiring selected IDs for every new live recorder, and pairing the reserve migration. The independent static reviewer agreed this is a safer semantic separation, subject to the regressions listed above. It remains review-only until the exact revised artifact is reviewed and an implementation path is authorized.
