## 3. Destination selection

Smallest page change (about 5 files):
1. Add a destination list above the direction tabs in routes/bridge/+page.svelte (a radio group or listbox). The selected destination replaces the single `config` the page holds today (:69); `BaseWalletBar` and both forms already take `config.chain` as a prop, so the EVM destinations need no form rewrite, only parameterised copy.
2. Replace `loadBridgeConfig()` (bridgeActor.ts:99) with a `loadDestinations()` that returns one view per destination: id, family (evm, solana, sui, xrpl), display name, chain identifier (a string, because Solana, Sui and XRPL ids are not numbers), network label (mainnet or testnet), status (enabled or disabled), plain-language reason, limits and fees. Until the canister exposes profiles, synthesise the Base entry from `get_bridge_info` exactly as `resolveBridgeConfig` does today.
3. Put a `DestinationWallet` interface between the page and each wallet family (connect, disconnect, account, network id, onChange, availability). The EVM implementation wraps `createEvmWalletStore`; the XRPL one wraps #586's `XrplWalletAdapter` (xrplWalletService.ts:80-98), which already has this shape.
4. Make the saved-intent record carry a destination key. The same 0x address is valid on all six EVM chains, and `IcpToBaseIntent` has no chain field (intents.ts:28-42), so a recovery row reading "icUSD to 0x..." would not say where. Bump `INTENT_VERSION` (intents.ts:19); the existing `newer_version` read-only guard already protects older app builds.
5. How the page addresses a destination is an OPTION awaiting BB-33, not a requirement: either a destination argument on a shared interface (today the call takes `base_recipient`, did:87), or one canister per destination with the page choosing the actor to call. The per-destination option leaves the reviewed Base APIs unchanged.

Disabled destinations:
- Listed, visibly marked "Unavailable", with the profile's reason in plain words (for example "Not enabled yet: this network is still being verified"). Not hidden, because users should see what exists.
- Not selectable: `disabled`/`aria-disabled`, no click handler, not reachable by arrow keys. Selecting nothing leaves the page on the first enabled destination or an empty state.
- Forms, wallet bar and review panels are not mounted for a disabled destination, so no wallet prompt can start.
- Defense in depth: one function `assertCanSign(profile, walletState, fresh status)` called by every flow immediately before the first wallet or signer call. Two different states, kept distinct: a DISABLED destination (profile disabled) means no signing request in either direction; PAUSED releases on an active destination are existing Base behavior, where Base to ICP shows a warning that delivery will be held (BaseToIcpForm.svelte:395-396) and `send()` stays available (:299), and `bridgeBlocked` (IcpToBaseForm.svelte:67, 432, 477, 519) gates ICP to Base on deposit pause or halt. Groundwork does not change that Base behavior or add a Base fix or test gate for it; a future multichain page applies the disabled rule to both directions and keeps the paused warning as disclosed held delivery.
- The 60 s refresh (routes/bridge/+page.svelte:63) must be able to turn the selected destination to disabled mid-session; a Review panel open at that moment returns to the unavailable state, and Confirm re-reads status, in the way `fee_changed` re-reads the fee (IcpToBaseForm.svelte:492-497).

Where status comes from: only the canister (profile query or `get_bridge_info`, including `pauses`, `halted` and the binding). The static catalog in the page may hold names and icons, never an enabled flag. A destination the canister does not report renders as "Not configured". If the read fails, every destination renders unavailable (the page already does this for the single config, +page.svelte:109-118).

## 4. Safety requirements essential for a demo

1. Exact chain and network before signing: Review shows name, chain identifier, and "Mainnet" or "Testnet" (loud for testnet), next to the amount and recipient. Today it shows only the name (IcpToBaseForm.svelte:457, BaseToIcpForm.svelte:498). The wallet-bar badge shows the wallet's live network and flags mismatch (kept).
2. Amount in 8-decimal icUSD: keep `parseE8s`/`formatE8s` (bigint, never rounds, rejects a ninth decimal). Every chain's token uses 8 decimals (EVM contract `decimals()` 8; Solana and Sui `decimals` 8, display-only; XRPL follows the BB-33 and BB-37 choice: PR #586's issued currency by default, with its exact decimal parser, or `AssetScale` 8 metadata if a Multi-Purpose Token is chosen later). The review amount must come from the same bigint that is signed. Do not show wallet-side floating point amounts.
3. No signing request when the selected destination is disabled: see section 3. A unit test per flow that a disabled profile makes zero wallet calls belongs to future implementation (section 6), not to groundwork.
4. Recipient validation per family before Review: EVM keeps EIP-55 (icpToBase.ts:93-111); Solana, Sui and XRPL need their own validators (formats not specified in the facts files; confirm against each chain's docs). Default the recipient to the connected account of the selected family, as IcpToBaseForm.svelte:112-114 does for EVM.
5. XRPL holder opt-in explained before the first transfer. The representation is the BB-33 and BB-37 choice; the default is PR #586's trust-line issued currency, which needs the holder's TrustSet (xrplIcusdService.ts:10-14 builds it from backend config only). If a Multi-Purpose Token is chosen later (a BB-32 recommendation, recorded as an open decision), the holder submits `MPTokenAuthorize` instead; either way the issuer cannot do it for them. The page must:
   - show a "Step 1: enable icUSD on your XRPL account" card before the ICP-to-XRPL button, in plain words: one transaction signed in the XRPL wallet, it adds a balance entry to the account, and it needs XRP reserve (live ledger values 1 XRP base plus 0.2 XRP per owned object; the MPToken holder reserve is not stated in the sources);
   - state that without this step the delivery cannot land on XRPL and the escrowed icUSD stays safe and refundable (confirm the refund path with the canister card before using this sentence);
   - confirm the entry exists by a canister-mediated read, not by the wallet's claim, and keep the bridge button disabled until it does;
   - name the wallet the existing lane supports (PR #586 uses Xaman). If a Multi-Purpose Token is chosen later: Xaman 4.4.0 supports it but its opt-in UX is undocumented, and Crossmark and GemWallet support is not found in a primary source.
   Solana needs no holder step (the canister creates the associated token account; wallet display of Token-2022 is unverified). Sui and EVM need none.
