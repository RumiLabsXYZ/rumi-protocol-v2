# BB-32 Native-chain official-source facts: Solana, Sui, XRPL

Card BB-32 (worker W12), date 2026-10-30. Official-source facts only; nothing here deploys or activates anything.

Scope: the three non-EVM destinations for an escrow-backed icUSD representation (8 decimals, ICP threshold keys, no operator hot keys).

Conventions:
- Every row was verified 2026-10-30 against the cited primary source (chain foundation docs, official repos, DFINITY docs).
- "live query" means a read-only public JSON-RPC or GraphQL read made the same day (no transaction, no faucet, no wallet action) that confirms the cited doc.
- "not found in a primary source" means the official page read did not state it. Items marked "derived" are arithmetic on stated constants, not quotes.
- "Recommended representation" paragraphs are recommendations by the worker, not facts.
- Internal repo precedent (secondary, for orientation only): the repo's earlier Solana and XRP rails used threshold Ed25519 (`sign_with_schnorr`) and the DFINITY SOL RPC canister (docs/icp-solana-integration-playbook.md, docs/superpowers/specs/2026-06-14-xrp-native-rail-design.md). Those were debt-backed lending rails, not this design.

Recommended representation for groundwork (recommendation, not fact): create a Token-2022 mint with 8 decimals and only `MetadataPointer` + `TokenMetadata` (name, symbol, URI on the mint, no second metadata program), mint authority = the canister's threshold Ed25519 key, freeze authority unset, and none of `PermanentDelegate`, `TransferHook`, `TransferFee`, `Pausable`, `DefaultAccountState`. Holders need no action: the canister creates the recipient ATA with `CreateIdempotent` in the same transaction as `MintToChecked` and pays the rent. Fall back to classic SPL Token if a target wallet or venue mishandles Token-2022 (unverified, see Open questions). Redemption is holder-signed `Burn` plus a canister observation at `finalized`, so no freeze or delegate power is needed. State honestly: whoever controls the canister's upgrade authority controls minting, and losing the canister (not just the key) strands the mint authority.

Recommended representation for groundwork (recommendation, not fact): use an MPT, not a trust-line IOU. It is the only XRPL form that holds 8 decimals exactly at any realistic supply (the IOU's 15-digit limit breaks exactness above about 10 million icUSD) and MPTokensV1 is enabled on mainnet. Create one issuance with `AssetScale = 8`, an explicit `MaximumAmount`, `tfMPTCanTransfer` set, `RequireAuth` unset (holders opt in themselves with `MPTokenAuthorize`, one user action and a reserve), `CanClawback` unset, `CanLock` unset unless a pause is wanted (it cannot be added later without DynamicMPT). Issuer = an account whose master or regular key is the canister's threshold Ed25519 key (no DER or low-S handling). Do not blackhole. Test on Testnet or Devnet first (both may reset). Accept that XRPL DEX/AMM listing of MPT is not supported per the concept page, and that wallet MPT support varies.

- Ed25519 testing (correction to the "No local Ed25519 key" row above). The quoted doc is about the
  dfx local replica, which has no Ed25519 key. PocketIC is different: it can provision threshold
  Schnorr Ed25519 keys, and this worktree already has test seams that use them:
  `src/rumi_protocol_backend/tests/solana_m2_pic.rs` (lines 17-32: `schnorr_public_key` and
  `sign_with_schnorr` with `test_key_1` on an II subnet), `xrp_native_e2e_pic.rs` (lines 23-29 and
  269, key `key_1`, degrading to a gated subset when a build cannot provision the key) and
  `solana_m2_sign_pic.rs` (best effort: it may skip the signature assertion when the key is absent).
  These are existing seams, not proof that signing tests passed; none was rerun for this card.
  Mainnet-only is therefore not a local-test gate.
- Native token programs alone do not give the EVM contract's consumed-mint and bridge-out semantics
  (SPL `MintToChecked`, a plain SPL burn, or a Sui `TreasuryCap` mint or burn). Binding returns to an
  ICP account and making retried mints idempotent are design requirements for BB-33, BB-35 and BB-36.
- XRPL: open PR #586 already implements an escrow-backed issued currency with exact decimal parsing
  and caps (see `xrpl-pr586-inventory.md`). The Multi-Purpose Token row above is a recommendation, not
  a replacement for that lane; the choice is an open decision recorded in the BB-33 design.
