# Native XLM Lookout publishing

Maintain the private XLM project inputs in this repository and publish only the sanitized projection to the `rumi-native-xlm` Lookout project. The manifest is `docs/coordination/native-xlm-lookout-manifest.json`; its curated board, presentation, and priority sidecars sit in this directory. Lookout's GitHub repository is public, so keep project inputs and operational details here.

Keep two distinct status strings in `native-xlm-lookout-presentation.json`. `summary` is the technical status. `plainSummary` is 2–3 short sentences, normally 35–60 words and at most 600 Unicode codepoints. Write for someone outside the project: say what they can actually do today, the main thing preventing the next useful result, and what happens next, including whether Rob needs to act. Use ordinary words and read it aloud before publishing. Avoid hashes, task labels, test counts, acronyms, release codes, engineering chronology, and lists of technical caveats. Put the full evidence in the technical summary and cards. Keep the existing glossary unchanged unless a term actually changes. Update **both** summaries whenever task movement, blockers, priorities, or overall progress change. Source, test, merge, deployment, activation, signing, broadcast, and settlement are separate claims.

After a meaningful change, use the scoped manifest to run a dry-run, publish, then dry-run again. Require the second dry-run to report the board unchanged and presentation and priorities unchanged. Confirm the returned Lookout revision and readback before reporting publication.
