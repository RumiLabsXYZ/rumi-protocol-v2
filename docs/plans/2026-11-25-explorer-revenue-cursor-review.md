# EXP-03: cursor-based revenue repair decision

Status: proposed source-only repair, returned to Merritt for scope review. No implementation or release performed. November 25, 2026.

## Decision and visitor outcome

Recommend a **frontend-only fee reader using the existing `get_events_forward_filtered` endpoint**, with a fixed event-log boundary, resumable bounded scans, exact integer sums and explicit incomplete coverage. Do not begin with a backend upgrade or optimize the old whole-log query.

This serves a visitor asking how much borrowing fee the protocol recorded in a selected time window. The November 25 public Revenue check verified the repaired unavailable display, while one anonymous Borrow request to the old endpoint failed with IC0522 even at length 1. The earlier source delivery improved honesty; it has not restored readable borrowing totals. Change the next investment from further UI acceptance to this narrowly scoped reader repair.

The important assumption is that the existing cursor endpoint can serve bounded pages to the frontend. Current source and generated declarations support it; retained scorer evidence supports reuse, but does not prove the anonymous browser path or latency. A missing method, reply/decode failure or a trap on a bounded page changes the recommendation to a precisely evidenced backend compatibility/per-call cost issue. Do not presume a backend release or silently fall back to the failing whole-log method.

## Exact proposed scope

Modify the fee-total reader in `src/vault_frontend/src/lib/services/explorer/explorerService.ts`, its existing `explorerService.revenue.spec.ts`, and `src/vault_frontend/src/lib/components/explorer/lenses/RevenueLens.svelte` plus the existing rendered revenue tests. A small local pure helper is permitted only if needed to keep the page validation/accumulator testable. No dependency or framework additions.

1. Create one shared scan session for the 24h and 90d totals. Capture `asOfNs`, then a fresh bigint `H = publicActor.get_event_count()`; scan the immutable snapshot prefix `[0,H)`. Label the result as recorded through event `H-1` at the observation time. Late-appended events, including operations with earlier business timestamps, belong to a fresh snapshot; this is not a claim of finalized economic-period accounting.
2. From cursor `c`, request `min(2000,H-c)` with explicit Borrow and Redemption types. Require `next_start == c + requestedScan` while `c < H`, IDs strictly increasing inside `[c,next_start)`, and decodable expected variants. Reaching the live tail before H is a failed/inconsistent snapshot. If the live tail has grown, `reached_end=false` at H is acceptable: coverage is complete at the pinned boundary. H=0 can complete without page calls after the successful count read.
3. Process a page in temporary state and advance the committed cursor only after validation and accumulation both succeed. A transport retry uses the same uncommitted cursor. Duplicate/out-of-range IDs or conflicting repeated data fail the page; they must never inflate totals or be silently accepted. Empty matches advance normally. Failed partial pages are never cached as successful totals.
4. Sum only `borrow_from_vault.fee_amount` and `redemption_on_vaults.fee_amount`; known `redemption_transfered` records contain delivery information and contribute no additional fee. Keep the existing fee category scope: principal, accruing interest, reserve-redemption categories and liquidation proceeds are not added to the borrowing total. For each dated fee record, use `startNs <= timestamp <= asOfNs`. Optional timestamps must be decoded correctly; unknown time or malformed amounts must not become zero. Track undated counts and amounts separately for each fee category. A fully scanned stream with undated fee records remains incomplete for time attribution in that category.
5. Keep amounts, timestamps, cursors and counts as bigint. Format exact icUSD with integer quotient/remainder at eight decimals; do not round-trip exact values through `Number`. Compact visual approximations may remain only with clearly accessible exact values. Combined fees stay unavailable if any required component is incomplete. Existing analytics swap values are not upgraded to a claim of exact integer accounting by this repair.
6. Bound each user-initiated scan run to 25 sequential page calls (at most 50,000 log entries), with a single in-flight scan shared by both windows and cancellation on unmount. At the budget limit, retain the fixed snapshot and cursor in memory and show **Incomplete — scanned X of H records**, with **Continue** to resume another bounded run. Error gives **Unavailable — scan failed** and explicit retry from the last valid cursor. Do not impose a hidden lifetime ceiling and label the prefix complete. A new time window or refresh starts a new pinned session; completed totals retain their `asOf`/coverage metadata and use the existing short cache lifetime, with keys including backend, window and snapshot. No durable browser cache is needed.
7. Show a total, including zero, only when that category has complete prefix coverage and no unresolved timestamp/amount issue. During progress or historical uncertainty, any visible subtotal is labelled partial/known-dated and cannot feed the full fee headline. Explain undated historical records separately from an interrupted scan; repeated retries cannot repair missing timestamps.

This may require many page calls on a cold load. The bounded resumable UI is an explicit tradeoff for avoiding a backend release, not a performance claim. If that is unacceptable after scoped delivery evidence, reconsider a maintained fee index/aggregate as a separate backend scope. Do not add that infrastructure speculatively now.

The revenue activity list can continue to show its existing honest unavailable warning; replacing its filter/search/pagination is outside the chosen fee-total outcome. The positions/liquidation transparency plan is unchanged.

## Acceptance attached to the proposed change

Use the existing Vitest/rendered tests; revise the old page-number expectation for this fee reader while retaining its error-versus-zero coverage. Run only the changed focused cases and normal enforced checks when implementation is authorized. Existing passing evidence is reused; none is rerun for this document.

- Two windows share one count snapshot and page stream; sparse empty pages advance and a match beyond 25 pages is found after Continue, never mistaken for zero at the first budget boundary.
- Nonmonotonic timestamps, exact start/end inclusion, events just outside the window, and an append after H yield the documented snapshot total without early timestamp stopping or tail chasing.
- Synthetic fees above `Number.MAX_SAFE_INTEGER` sum and format exactly; borrowing and redemption remain separate, and transfer-completion records do not double-count redemption fees.
- Identical timestamps with different IDs both count; duplicate/out-of-range IDs, nonadvancing/skipping cursors, premature tail, malformed amounts, and first/later-page failures preserve the last valid checkpoint without a false complete result.
- Complete dated empty data renders exact zero. Undated fee records render historical uncertainty even after full traversal. Interrupted/budget-limited scans render partial coverage; exact totals and combined headlines appear only under the stated completeness rule. Independent swap data remains visible.
- Rendered check proves Continue, retry, cancellation and exact-value access using deterministic fixtures. No funded operation, live data fabrication or backend mutation is part of acceptance.
